# 简历改写范式

> 本文档是 `eric-coach` skill 的改简历执行手册。skill 运行「改简历阶段」时读取此文件，与「教练人设与方法论.md」配合使用，产出可直接给候选人的改后简历成稿。

---

## 术语缩写解码法

**用途**：拿到 JD 或候选人简历后，第一步不是动笔改，而是把里面的英文缩写和专业术语全部列出来逐一解码。候选人如果自己都说不清楚这些词，面试会直接卡在这里。

**执行步骤**：

1. 扫描 JD 和候选人简历，列出所有英文缩写与专业术语。
2. 每个词给三个维度的解释：
   - **中文含义**：这个词是什么。
   - **岗位语境**：在这个岗位里，它意味着候选人要具体做什么、懂什么。
   - **大厂在用它做什么**：世界级大厂（Google、字节、微软、OpenAI 等）在这个词背后做的是什么量级的事，让候选人建立参照系。
3. 解码完成后，逐条问候选人：「这个词你能用自己的话说清楚吗？能举例子吗？」——不能的，简历上就不该原封不动保留，或者要改成候选人真正能讲的表达。

**常见词解码示例**：

| 术语 | 中文含义 | 岗位语境含义 | 大厂用它做什么 |
|------|---------|------------|--------------|
| AI Infra | AI 基础设施 | 训练/推理的底层平台能力，包括算力调度、模型部署、数据管道 | Google、Meta 把这一层作为核心竞争力，支撑所有 AI 产品 |
| SIP | 会话初始协议 | 语音/视频通话的信令控制协议 | 所有运营商级电话系统、企业通信系统的基础协议 |
| WebRTC | 网页实时通信 | 浏览器内直接做音视频通话，不需要额外插件 | Google Meet、腾讯会议 Web 版的底层通信层 |
| ASR | 自动语音识别 | 把用户语音转成文字，AI 电话/客服的输入层 | 科大讯飞、微软 Azure Speech 的核心业务 |
| TTS | 文字转语音 | 把 AI 回复转成语音播出，AI 电话/客服的输出层 | ElevenLabs、字节 Seed-TTS 在做的方向 |
| RAG | 检索增强生成 | 让 LLM 先检索文档再回答，解决知识截止和幻觉问题 | 企业知识库、智能客服、法律/医疗问答的标准架构 |
| TMS | 运输管理系统 | 管运输订单、调度、路线、运费结算的业务系统 | 物流公司（顺丰、UPS）和制造业的核心操作系统 |
| WMS | 仓储管理系统 | 管仓库入库、拣货、库存、出库的业务系统 | 电商（亚马逊、京东）仓储网络的核心系统 |
| SaaS | 软件即服务 | 按订阅卖软件，客户不买断、云端交付 | Salesforce、Slack、Notion 的商业模式 |

**目标**：辅导结束时，候选人能用自己的话、具体的例子，讲清楚简历上出现的每一个技术词。这是进入面试前必须完成的基础动作。

## 体验闭环抽象法

**用途**：候选人往往有多个零散项目，分开列出来会让面试官觉得「就是做了一堆功能」。把这些项目抽象成一条用户体验闭环或产品故事线，面试官能一眼看出候选人的产品思维是否完整。

**操作步骤**：

1. 列出候选人在同一业务场景下的所有项目/功能。
2. 找共同的用户价值主线：这些项目合起来，解决了用户旅程的哪一段？用户从「有问题」到「问题解决」经历了哪几步？
3. 用一句话命名这条主线（格式：「A → B → C」或「用户能 X / 能 Y / 不用 Z」）。
4. 把各个项目作为这条主线的节点重新叙述。

**充电场景完整示例（照实套用）**：

原始项目列表（零散）：
- 进站引导地址优化
- 电压不匹配的充电桩标签
- 充电排队等待信息展示

单独列三条经历，面试官看到的是「做了三个充电功能」。

抽象后产品故事线：**「找得到 → 开得到 → 不用等」**

- 找得到：进站引导地址精准，用户能导航到充电桩
- 开得到：电压匹配标签，用户不会充一半发现不兼容
- 不用等：排队信息透明，用户知道要等多久

这是完整的用户体验闭环。面试官看到这条线，能问出有深度的问题（「这三个方向优先级怎么排的？」「闭环里哪个环节用户流失最多？」），候选人也有故事可以讲。

**能力下线时如何替换一环**：

如果某个功能后来被砍了（如充电排队信息因数据源断了被下线），不要从简历里删掉这条线，而是替换闭环中的一环。

示例替换：「不用等」这一环 → 改成「到达时充电费用预估」——用户知道这次充电大概花多少钱，同样是在解决「不确定性」这个核心问题，逻辑上仍然成立。

面试时说法：「排队信息这个功能因为数据源的原因下线了，但我们当时把这一环替换成了到达时的费用预估，同样是在降低用户决策时的不确定性。」这比「功能被砍了」更显产品思维。

**找不到主线时**：

不是所有项目都能抽象成一条线。如果经历真的分散，宁愿选 2-3 个最能证明核心能力的项目重点写，其余简略提或不提。不要强行造一条不存在的线。

## 项目改写模板

**核心原则**：每段项目经历按「背景/问题 → 你的动作 → 产品价值/数据结果」三段式组织。优先量化，量化不了的用行为结果描述。

**三段式模板**：

```
【背景/问题】
[业务场景 + 用户遇到的具体问题，1-2 句]

【你的动作】
[你具体做了什么决策或设计，不是「参与」，是「你做了什么」，1-3 句]

【产品价值/数据结果】
[用户体验改变了什么，或业务数字变化，1-2 句]
```

**量化优先级**：
- 最好：有具体数字（转化率 +12%、客诉率下降 30%、DAU +2万）
- 其次：有行为描述（充电成功率提升、用户等待时间缩短、客服处理时长从 8 分钟降到 3 分钟）
- 兜底：有明确的问题-解法闭环，哪怕没有数字

**示例①（充电场景，有数据）**：

```
【背景/问题】
充电桩进站导航地址与实际入口偏差，用户导航到站后找不到入口，15% 用户放弃充电。

【你的动作】
牵头采集 200+ 充电站实际入口坐标，设计「精准引导地址」字段，协调地图 SDK 团队完成数据接入与展示改造。

【产品价值/数据结果】
上线后用户进站放弃率下降 40%，充电转化率提升 12%。
```

**示例②（AI 电话场景，无精确数据）**：

```
【背景/问题】
传统 AI 外呼系统语音延迟高达 3 秒以上，用户感知明显，中途挂断率高。

【你的动作】
主导 ASR + LLM + TTS 全链路延迟拆解，识别 TTS 合成为最大瓶颈，推动切换流式 TTS 方案，并设计端到端延迟监控看板。

【产品价值/数据结果】
端到端延迟从 3.2 秒降至 1.1 秒，用户中途挂断率下降，通话完成率显著提升。
```

**改写时常见错误对照**：

| 改前（不该这样写） | 改后（正确写法） |
|----------------|---------------|
| 负责产品迭代 | 主导 X 功能从 0 到 1 设计，解决了 Y 问题 |
| 参与 AI 项目开发 | 作为唯一 PM 负责 AI 电话产品的需求定义与上线，覆盖 ASR/LLM/TTS 全链路 |
| 用户体验有所提升 | 核心操作步骤从 5 步缩短到 2 步，任务完成时间下降 35% |
| 负责多个功能模块 | 负责充电「找得到 → 开得到 → 不用等」完整体验闭环的产品设计 |

## JD 对齐与选择性强调

**核心原则**：一份 JD 往往有十几条要求，候选人不需要全部满足，只需要在招聘方最在乎的 2-3 个核心点上让对方觉得「这人懂」。被长清单吓到或试图逐条覆盖，是常见的错误。

**执行步骤**：

1. 读完 JD，把所有要求列出来。
2. 拆分：哪几条是「不满足基本没戏」的真门槛，哪几条是「有了加分、没有也能进面试」的加分项。
3. 把候选人经历只对齐「真门槛」那几条，确认有没有直接证据。有直接证据的，重点展开；没有的，不要生造或模糊带过。
4. 加分项里，候选人真正有的，挑 1-2 个顺带提；没有的，不提。

**实战范例（AI 外呼产品 PM 岗）**：

JD 部分要求（原文）：
- 熟悉 SaaS 产品设计与商业模式
- 有 AI / 语音 / NLP 相关产品经验
- 精通 Python、Java 等多种开发语言
- 了解 ASR、TTS、LLM 技术原理
- 有 B2B 销售或客户成功经验
- 熟悉电话运营商协议（SIP、WebRTC 等）
- 英语流利

拆解结果：
- **真门槛**（不满足没戏）：AI/语音产品经验、了解 ASR/TTS/LLM 技术原理、熟悉 SaaS
- **加分项**（有了更好，没有不死）：精通多种开发语言、SIP/WebRTC 协议、B2B 经验、英语流利

候选人实际情况：有丰富产品经验 + 熟悉 SaaS + AI 开发经验 + 做过 AI 电话项目（真正跑通过 ASR+LLM+TTS 链路）

**正确做法**：重点在简历上打「AI 电话项目真实落地经验」+「ASR/TTS/LLM 全链路认知」+「SaaS 产品背景」，这三点直接命中真门槛。「精通多种开发语言」这条不是候选人强项，不要强写，面试官深挖只会减分。

对候选人说：「你不需要满足他们每一条要求。这个岗位最在乎的是你真的做过 AI 电话，懂技术链路，有 SaaS 感。你在这三点上有直接证据，这就够了。」

**选择性强调的关键判断**：

真正匹配的点，要写深、写具体（有数据、有细节、有决策过程）。
不匹配的点，不写、或轻描淡写一句带过。
加分项有真实经历的，放在技能列表或项目末尾顺带提。
没有的加分项，不造，不模糊带过——面试被深挖到就是减分。

**复合型选手：重定义赛道，别跟纯开发拼门槛**

当 JD 是「开发岗」，但候选人是「产品 + 开发」复合型时，不要逐条去满足开发门槛（语言、年限、框架）——那是拿自己的短板硬碰别人的长板。正确做法是重定义匹配赛道：

1. **找 JD 里能容纳复合型的信号**：「核心成员」「技术合伙人」「股权激励」「从 0 到 1」「真实项目经验者优先」——这些说明招聘方要的不只是一双手，而是能扛事、有判断的人。
2. **切换叙事**：从「我会写代码」切换成「我做过真实项目 + 我有产品/架构判断」。复合型的价值不是某一项最强，而是能独立跑通一个产品的全链路。
3. **一旦 JD 出现「技术合伙人 / 核心成员」类字眼，这就是复合型选手的主场**——直接打「合伙人叙事」：真实落地的项目 + 商业/产品判断 + 端到端交付能力。

范例（接上面的 AI 外呼岗）：JD 写了「特别优秀者可技术合伙人模式」。候选人不该去拼「精通 Python / 5 年开发」，而该打「我有真实落地的 AI 电话产品 + 12 年产品判断 + 能独立交付」，把自己放进合伙人赛道，而不是初级开发赛道。

判断口诀：**纯开发岗看门槛，合伙人岗看战绩 + 判断。复合型选手永远往后者站。**

## 改后简历硬约束

改完简历输出成稿之前，对照以下检查清单，全部通过才能给候选人。

**成稿，不是大纲（最重要的一条）**

交付的必须是一份**可以直接拿去投递**的完整简历，不是结构骨架、不是带一堆 `【填】` 占位符的模板。这是最容易犯、也最致命的错误——产出看着像简历，实则是张待填表，候选人根本用不了。

- ❌ 大纲（不合格）：`【接得通】对接 Twilio 与 Telnyx… — 结果：通话接通率【填】%` —— 候选人还得自己写
- ✅ 成稿（合格）：`主导对接 Twilio 与 Telnyx 双通信平台，打通 SIP 外呼链路，支撑 AI 外呼与电话客服的稳定通话能力，单实例稳定支撑数十路并发。` —— 拿来就能投

**缺数据怎么办（别用占位符糊弄过去）**：

1. **首选——先要数据再动笔**：改简历之前，先把关键数字问候选人要齐（接通率、并发数、延迟、自动解决率、转化率等）。拿到真数据，写进成稿。这一步前置，不要带着一堆空格往下走。
2. **真要不到数字**：用**写完整的行为结果句**替代，把整句话写完（如「端到端语音延迟显著下降，通话中途挂断明显减少」），而不是留半截句子加 `【填】`。
3. **整份简历最多保留 1-2 处**必须候选人本人确认的具体数字空位，且单独列一个「待你确认」清单提醒他补——绝不允许整份简历是一张待填表。

**判断标准**：把产出读一遍，如果候选人**不补任何东西就能直接投递**，才算成稿；如果他还得回去填一堆空、自己组织语言，那就还是大纲，打回重写。

**格式要求**：

- Markdown 格式，可复制、可直接贴入常见简历工具（超级简历、飞书文档、Word）
- 不使用表格（表格复制到 Word 后格式容易乱）
- 每段项目用三段式（背景/问题 → 动作 → 结果），段与段之间空一行

**内容必含**：

- 每段项目经历必须有体验闭环或产品故事线的抽象（至少一句话点出这段经历的用户价值主线）
- 每段项目优先包含量化数据；无数据时，有明确的行为结果描述
- 技能列表里的技术词，候选人必须能在面试中解释清楚——不能解释清楚的，从简历里删掉

**对齐要求**：

- 与目标 JD 的真门槛显式对齐：改后简历的核心亮点，要能直接回答「这个候选人满足了 JD 最重要的哪几条」
- 不堆砌：核心亮点不超过 3 个，其余降级为支撑材料或不展示

**禁止事项**：

- ⛔ 不写候选人做不到、讲不清楚的内容
- ⛔ 不用「熟悉/了解/接触过」这类模糊词，除非真的只是了解层面——如果候选人真做过，就写「负责/主导/设计/落地」
- ⛔ 不平铺所有经历：选择比堆砌重要，真正匹配 JD 的经历重点写，不匹配的简略或不写
- ⛔ 不造数据：没有的数字不捏造，用行为结果替代
- ⛔ 不交大纲：不把结构骨架、满是 `【填】` 占位符的模板当成稿交付——缺数据先去要，要不到就写完整的行为结果句

**输出前最后一问**：

看着改后的简历，问自己：「面试官 30 秒扫完这份简历，会记住什么？」

如果答案是清晰的 1-2 个亮点，通过。如果答案是「很多东西」或「说不清楚」，继续做减法。
