- [ ] T10 ⛔ 给自动化一个不会过期的 Chrome 入口 —— **这是现在最高优先级**
      2026-08-06 22:00 首次全自动运行的真正教训不是那两个 bug，是这一条：

      **Chrome 150 的「Allow remote debugging」是会话级授权，会过期。**
      实测（22:20，代理停掉后再连仍超时 → 排除并发限制，确认是授权失效）：
      授权失效后，已建立的连接还能续一会儿，**新连接一律拒绝**；
      代理重启后 `connected:false`，整条浏览器链（采集/发布/数据回收）全部瘫掉。

      也就是说：只要靠人去 chrome://inspect 勾一下，无人值守就是假的 ——
      人一走、Chrome 一重启，第二天所有任务静默失败，而且失败得毫无声音。

      候选解法：另起一个专用 Chrome 实例，带 `--remote-debugging-port=9222`
      和独立的 `--user-data-dir`（命令行起的实例不需要那个开关），
      在里面登录一次小红书，cookie 留在该 profile 里。
      代价：要在新 profile 里手工登录一次。
      验收：重启 Chrome / 重启机器之后，不碰任何开关，cdp-proxy 的
            /health 仍返回 connected:true，且 auto_publish 能跑完一篇。

      ✅ 2026-08-06 22:50 已搭好，**只差在新 profile 里登录一次小红书**：
        · com.eric.xhschrome —— 专用 Chrome，端口 9333，
          --user-data-dir=~/.xhs-chrome-profile，RunAtLoad + KeepAlive。
          实测 /json/version 直接应答（Chrome 151），**完全不需要那个开关**。
        · com.eric.cdpproxy 加 EnvironmentVariables: CHROME_DEBUG_PORT=9333，
          /health 已返回 connected:true, chromePort:9333。
        · set_schedule.mjs / click_probe.mjs / focus_tab.py 三处连接层统一改成
          「先问 9333 的 HTTP 端点，拿不到再兜底读日常 profile 的 DevToolsActivePort」。

      ⚠️ 改了共享 skill 文件 `~/.claude/skills/web-access/scripts/cdp-proxy.mjs`，两处：
        1. 新增 CHROME_DEBUG_PORT 环境变量（不设＝原行为，向后兼容）。
           不加这个，自动发现会一路选中日常 Chrome 的 9222 —— 那个端口
           TCP 通但不应答，checkPort 只做 TCP 连接检查，必然误判为可用。
        2. **修了一个真 bug**：`getWebSocketUrl` 在没有 wsPath 时拼的是
           `ws://host:port/devtools/browser`（不带 UUID），现代 Chrome 早已不认，
           必然「连接失败」。改成从 /json/version 取真正的 webSocketDebuggerUrl。
           这个 bug 影响所有「靠端口扫描发现 Chrome」的场景，不止本项目。

  已有端点：/new /navigate /eval /click /clickAt /setFiles /scroll /screenshot /info。

  所以接力检测到发布后回填的时间必须是**页面上真实选中的那个**，不能拿建议值顶替，
  否则 7 个时段的对比样本会偏。
