口径：标准 API 单价折算的**额度等价成本**，不是现金账单（订阅已覆盖）。
Opus 5 $5/$25、Sonnet 5 $3/$15；缓存写 1h = 2×、5m = 1.25×、读 = 0.1×。

> ⚠️ 与 8/11 那份的差异：上一版按 jsonl 行统计 usage，把**同一个 API 响应的多个
> content block（thinking / text 分行落盘）重复计了一次**，单次成本约虚高一倍。

> 优化幅度的结论不变，绝对值要以本文为准。

三个可核对的交叉验证：
- 写稿 prompt `--dry-run` 实测 50,034 字 ≈ 40k token，加 26.1k 固定 = 66.5k，与实测写缓存 66.5k 吻合

两个此前没被量化的事实：

1. **CLI 固定开销占单次成本的 27–65%**，且它 100% 走 1h TTL 缓存、付 2 倍价，
   而读/写缓存比只有 0.03 —— 写进去的缓存几乎没人读。
2. **输出里 70–80% 是 thinking token**。写稿输出 12.2k token，落到成稿正文的只有
   2,946 字（≈2.4k token）；审核 9.3k 输出里正文 3,659 字（≈2.9k token）。

## 三、CLI 固定开销：38.7k 不是地板，17.5k 才是

`headless_cli.py` 的注释写「38,704 是 CLI 路径下的地板价，`--bare` 因为跳过 keychain
不可用」。这个结论过期了 —— **`--safe-mode` 禁掉 CLAUDE.md / skills / plugins / hooks /
MCP，但明确保留 auth**（`--help`：Auth, model selection, built-in tools, and permissions
work normally）。实测（同一句 5 字 prompt，空 cwd + 禁全部工具）：

| 配置 | 输入合计 | 新写 1h 缓存 | 读缓存 | 该次成本 |
|---|---:|---:|---:|---:|
| 现状（空 cwd + 禁工具） | 38,811 | 26,106 | 12,703 | $0.268 |
| + `--safe-mode` | 17,487 | 4,782 | 12,703 | $0.054 |
| + `--safe-mode --disable-slash-commands` | 14,771 | **2,689** | 12,080 | **$0.033** |
| + `--safe-mode --system-prompt "…"` | 14,819 | 14,817 | **0** | $0.148 |

**每次省 23.4k 新写缓存 = $0.234。**

⛔ 反直觉的一条：**自定义 `--system-prompt` 反而更贵**。默认 system prompt 里那 12k
是跨会话共享的缓存读（0.1×），换成自己的 system prompt 就变成每次全新写入（2×）——
token 少了 5%，成本涨了 4.5 倍。**不要动 system prompt，只动 safe-mode。**

落地风险已核查：审核/写稿的 prompt 都把 skill 正文内联进去了（审核 prompt 里
`skills/eric-xhs-audit` 全文照抄），不依赖 CLI 的 skill 发现；CLAUDE.md 引用 0 次；
工具早已全禁。safe-mode 对这条链路是纯减法。

## 四、最大单点：交互式会话把上下文养到 1M 才 compact

交互式开发 8 天 $1,137，成本结构和自动化完全相反：

| | 占比 |
|---|---:|
| **读缓存（0.1×）** | **73%（$835）** |
| 写 1h 缓存 | 17%（$191） |
| 输出 | 10%（$111） |

读缓存不值钱（0.1×），但架不住量：46 个会话读了 **1,670M token**。原因是长会话的
上下文是**二次增长**的 —— 每多一轮，后面每一轮都要把它再读一遍。

实测本机最大的一个会话（927 次请求，读缓存合计 **434M = $217**）：

| 请求区间 | 该次读缓存均值 |
|---|---:|
| 0–92 | 127k |
| 184–276 | 375k |
| 368–460 | 600k |
| 552–644 | 792k |
| 644–736 | **917k**（峰值 980k，已顶到 1M 窗口） |
| 736–828 | 229k ← 这里才 autocompact |
| 828–927 | 219k |

**上下文一路涨到 980k 才触发压缩。** 前 736 轮里，每一轮都在为一个越来越胖的上下文
付读缓存钱。若把 autocompact 窗口设到 200k，这个会话的读缓存从 434M 降到约 185M，
**单会话省 $124**。

按同样口径估全量：交互式 46 个会话若统一 `--autocompact 200000`，读缓存 $835 →
约 $370，**一周省约 $400**。这一条的收益是自动化全链路优化的 8 倍以上。

## 五、模型选择：实测 A/B（审核链路）

同一篇成稿 `成稿_2026-08-17_面试官看出能力差.md`（审核 prompt 40,916 字），
跑 5 组配置。审核输出是一行 CSV + 完整报告，**总分直接决定发不发布（85 分线）**，
所以质量判据不是"读起来像不像"，是分数和字段格式。

| 配置 | 模型 | 写缓存 | 输出 | 成本 | 耗时 | 总分 | 可用性 |
|---|---|---:|---:|---:|---:|---:|---|
| A 现状 | Opus 5 | 64.1k | 9.3k | $0.879 | 183s | **86 绿** | 基线 |
| B +safe-mode +禁 skills | Opus 5 | 40.7k | 11.3k | **$0.696** | 225s | 84 黄 | ✅ 可用 |
| C +safe-mode | Sonnet 5 | 14.3k | 17.4k | $0.380 | 234s | **79 黄** | ❌ 判定偏严 |
| D +safe-mode +effort medium | Sonnet 5 | 39.9k | 6.1k | $0.336 | 98s | 86 绿 | ❌ **格式错位** |
| **E +safe-mode +effort medium** | **Opus 5** | 52.7k | **6.9k** | **$0.699** | **136s** | **87 绿** | ✅ **最优** |

### C（Sonnet 5）为什么不能用：不是判错，是判严

三个配置都注意到了同一处 —— CTA 里那句给面试官的引语「那你随便说说思路」。差别在判定：

- **A（Opus）**：属话术模板对触发场景的预演，未归属给具体人，不构成转述型编造 → 不扣分
- **B（Opus+safe）**：判边界情形、不算红线，但建议去掉引号消歧 → 不扣分，写进建议
- **C（Sonnet）**：「三库均查无出处」→ 直接写进**红线列**并扣分

C 的判法正是 T2 台账里点名的**最大风险**：把「库里没有」误判成「编造原话」。
它在 6 个维度上普遍比 Opus 低 1–4 分（24/31/7/6/7 vs 28/30/8/7/8）。

换 Sonnet 审核省 $0.44/次，但一次误判返工的代价是 **写稿 $0.98 + 复审 $0.82 = $1.80**。
**返工率只要上升 25%，这笔账就是负的。** 除非同时用一批平行样本重新标定 85 分线 ——
标定本身的成本高于它能省下的钱。

### D（effort medium）为什么不能用：格式静默错位

D 的总分 86、成本最低、耗时只有基线的一半，看上去最优。但它输出的 CSV 是错的：

```
A：…,86,绿,搜索流,28,30,8,7,8,-,5,无,-,…      ← 第 5 字段起是 6 个维度分
D：…,86,绿,搜索流,面试官能力差-卡壳应对,33,7,7,8,-,5,无,-,…  ← 多插了一列，维度只剩 4 个数
```

`audit_one()` 的解析判据是「含文件名且逗号 ≥14」，D 这行**能通过判据**，然后
`fields[12]`、`decide_disposition()` 全部取到错值 —— 不报错，直接把错的处置写进
`审核记录.csv`。报告正文也从 9,799 字缩到 5,350 字（−45%）。

### E（Opus + effort medium）是最优解

D 的格式错位一度让人以为是 effort 降档的锅。**E 推翻了这个归因** —— 同样是
`effort medium`，Opus 输出的 15 个字段一字不差：

| | 总分 | 六维分 | 字段数 | 报告长度 |
|---|---:|---|---:|---:|
| A 基线 Opus/high | 86 | 28,30,8,7,8 | 15 ✅ | 9,799 字 |
| **E Opus/medium** | **87** | **28,30,9,7,8** | **15 ✅** | **11,028 字** |
| D Sonnet/medium | 86 | 33,7,7,8（错位） | 15 ❌ | 5,350 字 |

E 的六维分和基线只差 1 分（第三维 8→9），报告比基线还长，指出的问题更具体
（「第三秒」是全篇唯一无来源精确数字且与后文「十秒」矛盾 —— 基线没提）。
**格式遵循度是模型层面的能力，不随 effort 降档而丢失；Sonnet 丢，Opus 不丢。**

推荐配置：**`--safe-mode --disable-slash-commands --effort medium`，模型保持 Opus 5。**

- 实测 $0.879 → $0.699（−20%，E 这次写缓存 52.7k 偏高是缓存命中噪声）
- 理论稳态：固定 2.7k + 内容 31.8k = 34.5k 写缓存 $0.345 + 输出 6.9k $0.173 ≈ **$0.52（−41%）**
- 耗时 183s → 136s（−26%），定时任务串行跑十几篇时这个也值钱

⚠️ **单篇单次样本，不能直接上生产。** 84（B）和 87（E）都落在 85 线附近，
必须先用 8–10 篇历史成稿做平行复审，确认不是系统性偏移，再改脚本 —— 见台账 T1。

## 八、结论

1. **自动化生产流程已经不该是优化重点了。** 定时任务 $17.3/天，占总消耗 9%；
   上一轮定的 $45/天目标早已达成到 38%。天花板约每周 $73（含 8/18 追加的缓存改造）。
2. **钱在开发会话上（77.5%），而且是可修的浪费** —— 上下文养到 980k 才 compact，
   前 736 轮每一轮都在为一个越来越胖的上下文付读缓存。一个 `--autocompact 200000`
   顶得上自动化侧全部优化的 8 倍。
3. **模型不要降档，配置要降档。** Sonnet 5 在审核上判定偏严（79 vs 86），
   省下的钱不够赔返工；而 Opus 5 + `--safe-mode --effort medium` 分数持平（87 vs 86）、
   格式无损、成本 −20%~−41%、耗时 −26%。
4. **上一版的单次成本数字有一倍虚高**（流式 content block 重复计数），
   本文按 `message.id` 去重后重算，方法记在第 0 段的告警框里，以后别再踩。

## 附：8/18 追加实测（见 `20260818-缓存与prompt结构实测.md`）

回答 Eric 的四问后又挖出一条，比本文第三节的 safe-mode 更值钱：

**`claude -p` 的用户 prompt 完全不参与 prompt caching。** 同一段 prompt 一字不差重跑
三次，写缓存 76.1k 一次不少、读缓存恒定 15.7k；生产数据里批次内连跑 13 篇同样如此。
本文第二节说「写 1h 缓存占 69.3% 成本、读缓存只有 1.2%」——现在知道原因了：
**写进去的那部分从设计上就不会被读**。

推论：用户 prompt 每 1k token 的真实单价是 $10/M（2× 写入），不是 $5/M。

修法是把静态区（写稿 39.2k 字 / 审核 27.3k 字，两条链路都约占 2/3）搬到
`--append-system-prompt`。真实审核 prompt 实测：换一篇不同的稿，静态前缀照样命中
39.7k 读缓存，单次 $0.879 → $0.285，13 篇批次均摊 −64%。

⚠️ 代价是判分偏低 2–3 分（84/83 vs 基线 86/87），必须先做 8–10 篇平行复审 —— 台账 T2b。
