## 二、七条实测结论

### 1. 上一版的单次成本数字虚高一倍（方法错误）

上一版按 jsonl 行统计 usage，把**同一个 API 响应的 thinking / text 两个 content block
分行落盘的记录各计了一次**。按 `message.id` 去重后：

| | 8/11 报的 | 实际 |
|---|---:|---:|
| 写稿单次 | $2.06 | **$0.98** |
| 审核单次 | $1.13 | **$0.82** |

⛔ 以后任何 usage 统计都必须按 `message.id` 去重。这条写进 T4 的验收。

### 2. 定时自动化的真实日成本是 $17.3，早已达标

5 个有效运行日：8/11 $15.5、8/12 $20.4、8/13 $15.3、8/14 $15.6、8/16 $19.5 —— 很稳定。
上一轮定的 $45/天目标已达成到 38%。**继续压它的天花板是每周 $73。**

### 3. `claude -p` 的用户 prompt 完全不参与 prompt caching ⭐ 最重要

同一段 prompt 一字不差连跑三次：

| | 写 1h 缓存 | 读缓存 |
|---|---:|---:|
| ① 静态+问题A | 75.5k | 15.7k |
| ② 静态+问题B | 76.9k | 15.7k |
| ③ **和②完全相同重跑** | **76.1k** | **15.7k** |

生产数据印证：8/11 06:02 那批连跑 13 篇（间隔 2.5–5 分钟），读缓存**恒定 15.6k**。
那 15.6k 是 CLI 自己的 system prompt；用户 prompt 无论重复多少次都是全新写入、永不读回。

**推论：用户 prompt 每 1k token 的真实单价是 $10/M（2× 写入），不是 $5/M。**
写稿那 40k token 内容 = $0.40，审核 32k = $0.32，全是不可回收的沉没成本。
这解释了成本结构里「写 1h 缓存 69.3% / 读缓存 1.2%」——写进去的那部分从设计上就不会被读。

**副作用**：8/12 那次「静态在前动态在后」的前缀重排**在 CLI 路径下无效**。
共同前缀确实从 5.5% 提到 66.7%，但 cache_control 断点打在 system prompt 结束处，
用户消息整体不参与前缀匹配 —— 字符串对齐了，缓存边界没对齐。
`build_prompt` 里那 20 行注释必须一起改掉，否则下一个人会继续按错误模型优化。

### 4. 静态区搬到 `--append-system-prompt` 后缓存才真正生效

同一段 53k 字符静态内容，换个位置放：

| 配置 | 第 1 次 | 第 2 次起 |
|---|---:|---:|
| 现状（全塞用户 prompt） | $0.798 | **$0.798**（无衰减） |
| `--append-system-prompt` 承载静态 | $0.798 | $0.274（写 23.9k / 读 68.7k） |
| **+ `--safe-mode --disable-slash-commands`** | $0.571 | **$0.046**（写 1.2k / 读 67.4k） |

safe-mode 还能再降一截，是因为它去掉了 CLAUDE.md / skills 那部分每次可能微变的内容 ——
**前缀有一个字节不同，后面全部失效**，所以「减少 system prompt 体积」和
「稳定 system prompt 内容」在这里是同一件事。

真实审核 prompt 上的验证（静态 27,340 字 → system prompt，动态 13,576 字 → 用户 prompt）：

| | 写 1h | 读缓存 | 输出 | 成本 | 总分 | 字段 |
|---|---:|---:|---:|---:|---:|---:|
| A 基线（opus/high 全塞） | 64.1k | 12.7k | 9.3k | $0.879 | 86 | 15 ✅ |
| F1 safe+medium+append 第 1 篇 | 52.8k | 0.0k | 5.6k | $0.666 | 84 | 15 ✅ |
| **F2 换一篇不同的稿** | **10.1k** | **39.7k** | 6.6k | **$0.285** | 83 | 15 ✅ |

**F2 是关键：跨稿件复用成立**，不是只有同一篇重跑才管用。
13 篇批次均摊 $11.43 → **$4.09（−64%）**；写稿同口径估 **−66%**。

### 5. CLI 固定开销 38.7k 不是地板，14.8k 才是

`headless_cli.py` 注释说「38,704 是地板价，`--bare` 因为跳过 keychain 不可用」——**已过期**。
`--safe-mode` 禁 CLAUDE.md / skills / plugins / hooks / MCP 但**明确保留 auth**：

| 配置 | 输入合计 | 新写 1h | 读缓存 | 成本 |
|---|---:|---:|---:|---:|
| 现状（空 cwd + 禁工具） | 38,811 | 26,106 | 12,703 | $0.268 |
| +safe-mode | 17,487 | 4,782 | 12,703 | $0.054 |
| +safe-mode +禁 skills | 14,771 | **2,689** | 12,080 | **$0.033** |
| +safe-mode +自定义 system prompt | 14,819 | 14,817 | **0** | $0.148 ⛔ |

⛔ **不要用 `--system-prompt` 替换默认的**：默认 system prompt 那 12k 是跨会话共享的
缓存**读**（0.1×），换掉就变成每次全新**写**（2×）—— token 少 5%、成本涨 4.5 倍。
要加东西用 `--append-system-prompt`（追加，不替换）。

### 6. 模型不要降档，effort 可以降档

5 组 A/B（同一篇成稿）：

| 配置 | 模型 | 成本 | 耗时 | 总分 | 六维 | 可用性 |
|---|---|---:|---:|---:|---|---|
| A 现状 | Opus 5 | $0.879 | 183s | 86 | 28,30,8,7,8 | 基线 |
| B +safe-mode | Opus 5 | $0.696 | 225s | 84 | 26,31,8,6,8 | ✅ |
| C +safe-mode | Sonnet 5 | $0.380 | 234s | **79** | 24,31,7,6,7 | ❌ 判定偏严 |
| D +safe +medium | Sonnet 5 | $0.336 | 98s | 86 | **格式错位** | ❌ |
| **E +safe +medium** | **Opus 5** | $0.699 | 136s | **87** | 28,30,9,7,8 | ✅ **最优** |

- **Sonnet 不能用**：它把「话术模板的场景预演」判成「编造原话」写进红线扣分 ——
  正是 T2 台账点名的最大风险。省 $0.44/次，但一次误判返工赔 $1.80（写稿 $0.98 +
  复审 $0.82），返工率涨 25% 就倒亏。
- **D 的格式错位不是 effort 的锅**：E 同样 medium，15 个字段一字不差。
  **格式遵循度是模型层面的能力**。D 那行还能通过 `l.count(",")>=14` 的解析判据，
  会静默把错值写进 `审核记录.csv`。

### 7. 交互式会话把上下文养到 980k 才 compact

实测最大的一个会话：927 次请求，读缓存累计 **434M = $217（单会话）**。

| 请求区间 | 该次读缓存均值 |
|---|---:|
| 0–92 | 127k |
| 368–460 | 600k |
| 644–736 | **917k**（峰值 980k，顶到 1M 窗口） |
| 736–828 | 229k ← 这里才 autocompact |

`~/.claude/settings.json` 里 `model: opus[1m]`（1M 窗口）+
`CLAUDE_AUTOCOMPACT_PCT_OVERRIDE: 50` —— **50% 的 override 显然没按预期生效**，
否则应在 500k 触发。交互式成本 73% 是读缓存（$835 / 8 天）。

## 三、方法论（下次怎么复现）

1. **数据源**：`~/.claude/projects/<项目>/<session>.jsonl`，每条 `type=assistant`
   的 `message.usage`。⛔ **按 `message.id` 去重**（流式响应的多个 content block 会分行落盘）。
2. **成本口径**：`input×P + cw1h×P×2 + cw5m×P×1.25 + cr×P×0.1 + output×Po`，
   P 按 `message.model` 取。
3. **区分定时 vs 手动**：按 `timestamp`（UTC，本地 EDT = UTC−4）落不落在 10:00–19:00 窗口。
4. **测固定开销**：空 cwd + 禁全部工具，跑一句 5 字 prompt，看 `--output-format json` 的 usage。
5. **测缓存是否生效**：同一 prompt 连跑两次，看第二次 `cache_read_input_tokens` 有没有涨。
   ⛔ 不要用「共同前缀字符数」推断缓存命中 —— 那是 8/12 踩过的坑。
6. **测质量**：审核链路有 CSV 总分和六维分，是天然的 A/B 标尺；
   ⛔ 必须同时校验**字段数=15**，格式错位不报错。

## 四、改造方案（逐处）

### 改造 1 · `scripts/headless_cli.py`
```
HEADLESS_FLAGS = ["--disallowedTools", _DISALLOWED,
                  "--safe-mode", "--disable-slash-commands", "--effort", "medium"]
```
并更新文件头注释：38.7k 不是地板价，14.8k 才是；`--bare` 不可用的结论保留，
但要写清 `--safe-mode` 是可用的替代。

### 改造 2 · 三个链路的 prompt 拆成 静态 / 动态两段
| 脚本 | 切点 | 静态段 |
|---|---|---|
| `refine_loop.py::build_prompt` | 【本篇口径】之前 | ~39,200 字（知识框架 14,419 + 必须命中清单 11,045 + 硬编码红线 ~13,700 + 格式范例 1,023） |
| `independent_audit.py::build_audit_prompt` | `【词库.csv` 之前 | 27,340 字 |
| `auto_analyze.py` | skill 正文之后 | 待量化 |

函数改为返回 `(static, dynamic)`，调用方把 static 传 `--append-system-prompt`。
⛔ 静态段必须**逐字节稳定**：不含 `date.today()`、不含随机采样、不含 dict 无序遍历。

### 改造 3 · 删掉 `build_prompt` 里失效的前缀重排注释
那 20 行建立在「用户 prompt 参与前缀缓存」的错误假设上。改成指向本文结论 3。

### 改造 4 · `~/.claude/settings.json` 限制上下文窗口
`CLAUDE_AUTOCOMPACT_PCT_OVERRIDE: 50` 没生效，改用 `--autocompact 200000`
或核实正确的配置键。

### 改造 5 · 分数返工档加 `REWORK_FIX_PROMPT`
照 `MECH_FIX_PROMPT`（621 字 + 正文节，$0.38）的样子，只喂：
扣分点 + 当前正文节全文 + 命中的那几条规则 + 涉及的那几条料。
⚠️ 必须分档：局部扣分走定向修订，结构性扣分仍走全量重写。
建议审核 CSV 加 `修订类型=局部|结构` 字段。

### 改造 6 · `scripts/xhs-schedule` 挪到本地卷
`/Volumes/datacenter` 上的可执行文件在 launchd 上下文里被 macOS 拦（Operation not permitted），
导致 8/17 的 resume 静默失败、生产线停摆 2 天。

## 六、明确不做

- **审核换 Sonnet 5** — 判定偏严 79 vs 86，省的钱不够赔返工（结论 6）
- **自定义 `--system-prompt`** — 破坏 12k 共享缓存读，成本涨 4.5 倍（结论 5）
- **改走 Messages API 直调** — 无 API key，且订阅已覆盖；改造等于把额度消耗变成真实账单
- **用检索替代全量塞入** — 素材侧已做完（原话 553→60、案例 200→30、词库 1049→1 行）；
  剩下 78.3% 是必须全量生效的规则区，按主题挑几条会漏红线。
  **同样这批 token，解法是换位置（改造 2），不是砍掉**
- **给图库/范例做索引** — 前提不成立：写稿 prompt 里没有图库（图是产出 `cards.json`
  后另一条链路生成），历史范例只有 1 篇 1,023 字占 2%

- **继续压 prompt 字数** — 第一轮实测 prompt 砍 58%，成本只降 18%
