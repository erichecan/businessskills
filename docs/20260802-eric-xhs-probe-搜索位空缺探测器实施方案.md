# eric-xhs-probe · 搜索位空缺探测器 实施方案

> 2026-08-02 · 依据：`docs/20260731-搜索流转向决策与实施方案.md` 七条决策（优先级最高）+ hook-lab 架构借鉴。
> 目标：把 `词库.csv` 里大面积的「待探测 / 待验证」变成有依据的判定，让搜索流的选题环节真正跑起来。

---

## 0. 一句话定位

**给一个候选长尾词，自动探明它值不值得做、前排缺什么答案，并把结论写回词库。**

不是爆款拆解器。不产出「为什么能爆」，产出「这个搜索位有没有空缺」。

---

## 1. 为什么是这个东西（问题定位）

当前瓶颈不在成稿，在**选词**：

| 证据 | 说明 |
|---|---|
| `xhs/素材库/词库.csv` 66 行，竞争密度列大面积「待探测」 | 决策 1 的「好词三条件」目前**没有任何自动化手段去核验**，全靠人肉搜 |
| `案例库.csv` 仅 C001 完整，C002 起全是「待补充」 | 案例供给靠回忆，缺外部触发源 |
| `评论区原话.csv` 仅 2 条 | 决策 6 的原话采集系统还没有稳定进料口 |
| `高热结构库.md` 已 583KB | 旧范式的产物还在持续膨胀，但决策已将其降为「推荐流参考，不再驱动生产」 |

**结论**：采集侧仍在按旧范式全速运转（记忆库 5076 行、每日 xlsx），而新范式所需的三张表（词库 / 案例库 / 原话库）处于半空状态。探测器就是补这条进料管。

## 2. 从 hook-lab 拿什么、不拿什么

来源：`github.com/hongfamonvAI/hook-lab`（3 个文件，约 12KB）。

| hook-lab 的做法 | 本方案 | 理由 |
|---|---|---|
| 提取脚本只吐客观 JSON，绝不判断；LLM 只判断，绝不抓取 | ✅ 全盘照搬 | 现采集是 prompt 驱动，抓取与判断混在一起，失败即整轮报废 |
| 多级回退 + `_error` 字段（失败返回错误+已得部分，不返回假数据） | ✅ 全盘照搬，并扩展为 `_partial` | 直接对应日志里反复出现的验证码拦截 |
| append-only 累积库、每条固定字段 | ✅ 照搬思路，但**写 CSV 不写 markdown** | 高热结构库 583KB 自由文本已证明：markdown 累积库不可机读、不可统计、不可反查 |
| 分析产物直接指向生产 | ✅ 照搬 | 探测结论必须落到词库列上，不能停在"洞察" |
| 6 段分析框架（互动率 / 前3秒 hook / 为什么能爆 / 改写方向） | ❌ **不要** | 这是推荐流爆款逆向工程，与决策 1、决策 5、决策 4「只盯搜索进入占比」直接冲突 |
| 「不要泛泛而谈」的措辞约束 | ❌ 不指望 | 它同样是裁判即运动员，解决不了 `xhs/工作台.md:44` 标红的主观自评问题 |

**本方案对 hook-lab 的关键改进**：竞争密度**不交给模型判断**，而是脚本里的确定性阈值规则。模型只做无法量化的那一件事——答案空缺。这正面回应工作台诊断出的「🔴 虚：全是主观自评，90 分门槛形同虚设」。

## 3. 总体架构

```
                    ┌──────────────────────────────────────┐
输入：候选词        │  第 1 层 · probe.py（客观提取，无判断）│
（词库中状态=       │  web-access CDP + 登录态              │
 待探测/待验证）───→│  → probe_<date>_<slug>.json          │
                    └──────────────┬───────────────────────┘
                                   │ 客观数据 + 确定性阈值算出的 density
                    ┌──────────────▼───────────────────────┐
                    │  第 2 层 · SKILL.md（5 段固定框架）   │
                    │  模型只做：答案空缺 / 句式提取 /      │
                    │  原话筛选 / 意图强度 / 场景类型       │
                    │  → probe_<date>_<slug>.result.json   │
                    └──────────────┬───────────────────────┘
                                   │
                    ┌──────────────▼───────────────────────┐
                    │  第 3 层 · backfill.py（脚本回填）    │
                    │  词库.csv / 评论区原话.csv /          │
                    │  案例采集卡.md / 运行日志.csv         │
                    └──────────────────────────────────────┘
```

三层严格分离。第 1 层失败不影响已得数据；第 2 层不许联网；第 3 层不许模型自由发挥格式。

## 4. 第 1 层 · 提取脚本 `scripts/xhs-probe/probe.py`

### 4.1 接口契约

```bash
python3 scripts/xhs-probe/probe.py --keyword "晋升答辩被评委问倒怎么办"
python3 scripts/xhs-probe/probe.py --from-cikuku --limit 5   # 从词库取待探测词批量跑
python3 scripts/xhs-probe/probe.py --resume                   # 断点续跑
```

沿用 `scripts/xhs-health/*.py` 的既有约定：`REPO = Path(__file__).resolve().parents[2]`、`SUCAI = REPO / "xhs" / "素材库"`、`csv` 标准库、退出码非 0 表示需人工介入。

### 4.2 输出 JSON schema

写入 `xhs/素材库/探测原始/probe_<YYYYMMDD>_<slug>.json`：

```jsonc
{
  "keyword": "晋升答辩被评委问倒怎么办",
  "probed_at": "2026-08-02T14:03:11",
  "source": "xhs_cdp",              // xhs_cdp | web_fallback | manual
  "completeness": "full",           // full | partial | failed
  "_error": null,                   // 有值时说明中断原因，如 "captcha_triggered"

  "autocomplete": [],                // v1 不采集（合成事件触发不了，见 §4.6），保留字段
  "note_count": null,                // 网页端不提供总数，恒为 null（保留字段便于将来接口化）

  "top_notes": [                     // 前排 10 篇，不足则实得多少写多少
    {
      "rank": 1,
      "note_id": "69e8a098...",
      "url": "https://www.xiaohongshu.com/explore/69e8a098...",
      "title": "晋升答辩被问倒的三个瞬间",
      "likes": 1200, "collects": 340, "comments": 56,
      "published_at": "2026-05-11",
      "author": "xxx"
    }
  ],

  "comments": [                      // 前排若干篇的评论区原话，原样保留
    { "note_id": "69e8...", "text": "我上周答辩就是这样，评委一追问数据来源我就懵了" }
  ],

  "density": {                       // ← 脚本按确定性规则算，不经模型
    "verdict": "低",                 // 低 | 中 | 高 | 待探测
    "rule_version": "v2",
    "sample_size": 22,
    "likes_known": 20,
    "median_likes": 66.5,
    "low_like_ratio": 0.70,
    "title_match_ratio": 0.0,
    "reason": "前排点赞中位数 66.5，低赞(<100)占比 70% — 搜索位有空缺；标题精确匹配率仅 0%，无笔记正面回答此长句"
  }
}
```

### 4.3 竞争密度判定规则（确定性，写死在脚本里）

> **⚠️ 本节已按 2026-08-02 实测重写为 v2。原 v1 口径（笔记总数 + 下拉补全）在网页端不可得，见 §4.6。**

决策 1 的「好词三条件」原文是：有下拉补全 / 笔记数不为零但不多 / 前排赞藏一般。
实测后三条各自的落地口径：

| 决策原文 | 网页端可得性 | v2 实测口径 |
|---|---|---|
| 有下拉补全 | ❌ 取不到 | 用**标题精确匹配率**代理：前排标题命中 ≥半数核心词的比例。低 = 没人正面回答这个长句 |
| 笔记数不为零但不多 | ❌ 页面不提供总数 | 用**低赞占比**代理：前排点赞 <100 的比例。高 = 搜索位没被占满 |
| 前排赞藏一般 | ⚠️ 只有赞，无藏 | **前排点赞中位数** |

**判定表**（`rule_version = v2`）：

| 条件 | verdict |
|---|---|
| 中位数 ≤ 500 **且** 低赞占比 ≥ 0.40 | `低`（搜索位有空缺，优先做） |
| 中位数 > 3000 **或** 低赞占比 < 0.15 | `高`（已被高赞占满） |
| 其余 | `中` |
| 有效点赞样本 < 8 条 | `待探测`（**不允许用剩余维度硬推**） |

标题精确匹配率 < 0.20 时，在 `reason` 里附加「无笔记正面回答此长句」——这是空缺的独立信号，不参与 verdict 计算，供第 2 层判断时加权。

> ⚠️ **v2 阈值仍是拍的，必须校准。** 词库里有 12 个词的竞争密度是人工判过的（状态 = 已验证/放弃/已使用），
> 拿它们做回归：已标「低」的应算出「低」，已标「高」的应算出「高」。对不上就调阈值并升 `rule_version`。
> **校准前不得仅凭 verdict=高 就判「放弃」。**

### 4.4 回退链（照搬 hook-lab 的降级思路）

```
1. 搜索页拿到卡片 + 点开 ≥1 篇取到评论  → completeness=full
2. 只拿到卡片、评论为空（该词前排笔记本身评论少，或点击被拦） → completeness=partial
   （密度判定照常出，仅原话库本轮无产出）
3. 遇验证码 → 立即停止该轮，落盘已得数据，_error="captcha_triggered"，
              写 state 供 --resume，退出码 1
4. 页面 0 卡片 → 区分「真无结果」(页面有"没找到相关内容") 与「被拦」，
                前者 failed、后者 partial
5. Proxy 不可用 → 直接退出并提示先跑 check-deps.mjs，不做无谓重试
```

**绝不编造**：拿不到的字段写 `null`，`note_count` 解析不出就是 `null`，不用 `top_notes` 数量倒推。

### 4.5 反封控策略（本方案最大落地风险，必须做在第一版）

日志已证明：`高热结构库.md` 多次记录「连续多关键词、最新排序抓取后触发图片验证码，后续关键词返回"没找到相关内容"」。因此：

- **单次运行硬上限 5 个关键词**（`--limit` 默认 5，超过需显式传参）
- **词间随机延迟 45~90 秒**，页内滚动/点击之间 2~5 秒
- **排序固定用「综合」**，不用「最新」（日志显示最新排序更易触发）
- **一旦检测到验证码 → 整轮立即终止**，不重试、不换词硬撑；写 state 文件 `探测原始/.probe_state.json`
- **每日运行不超过 2 轮**，且与既有采集任务（0/6/12/18 点）错开
- 检测信号：页面出现「安全验证」「没找到相关内容」但 `autocomplete` 有值 → 判定为被拦截而非真无结果

### 4.6 实测修正记录（2026-08-02，CDP 实跑）

方案初稿有三处按经验假设，实跑后被推翻，已改：

| 初稿设计 | 实测结果 | 处置 |
|---|---|---|
| 读结果页「笔记总数」判断竞争密度 | **页面根本不提供总数**，全页扫不到任何 `N篇/N条` 文本 | 字段作废（恒 null），改用前排点赞分布，见 §4.3 |
| 采集搜索框下拉补全 | 用 `value` setter + 合成 `input`/`keyup`/`compositionend` 事件均**无法触发**建议请求，小红书有防护 | v1 不采集，改用标题精确匹配率代理 |
| 详情页取评论 | 卡片 href 是 `/search_result/<id>?xsec_token=...` 而非 `/explore/<id>`；`xsec_token` 是访问详情的**必需参数**，直连 `/explore/<id>` 返回空壳 | 必须在搜索结果 tab 内 `POST /click` `section.note-item a.cover[href*=<id>]` 打开，正则同时匹配三种 href 形态 |

另外两个实现细节：
- proxy 的 `/eval` 按**表达式**求值，多语句必须自包 IIFE，否则返回 `{"error":"Uncaught"}`
- `/clickAt`（真实鼠标）对视口外元素返回 `x:0,y:0` 且点击无效；`/click`（JS click）无此限制，取评论用后者

## 5. 第 2 层 · Skill `skills/eric-xhs-probe/SKILL.md`

### 5.1 定位

```yaml
name: eric-xhs-probe
description: |
  搜索位空缺探测。给候选长尾词，核验好词三条件、找出前排答案空缺、抓评论区原话，
  结论回填词库。搜索流范式专用，不做爆款结构分析。
  触发：/eric-xhs-probe、/探词、「这个词值不值得做」「探一下这批词」
```

### 5.2 五段固定框架（模型只做这五件事）

脚本已算完 density，模型**不得推翻**，只在 `verdict = 待探测` 时说明缺哪个维度。

**① 好词三条件核验回执**
直接复述脚本结论 + 三个维度的原始值。一句话给出「做 / 缓 / 放弃」。

**② 答案空缺（本框架唯一的核心判断）**
读 `top_notes` 标题 + `comments`，回答两问：
- 前排 10 篇**都在给什么答案**（归类，不超过 4 类）
- **没人给的是什么**——具体到「哪种处境的人没被回答」，禁止写「不够深入」「缺少案例」这类空话
- 交叉验证：评论区是否有人在追问前排没答的东西？有 → 空缺证据强；无 → 标注「空缺为推断，证据弱」

对齐决策 5：只抓「前排答案空缺」，**不抓内容本身**，不做结构拆解，不评价好坏。

**③ 标题句式提取**
只提取句式骨架，剥离具体内容。如「被X问倒怎么办」「X的三个瞬间」。禁止摘抄完整标题入库。

**④ 评论区原话筛选**
从 `comments` 中筛出符合决策 6「真话是短的糙的不完整的」的条目，按 `评论区原话.csv` 现有 5 列填：`日期,来源链接,用户原话,暴露的处境,候选词`。
- 原话**逐字保留**（含错别字、繁体、口语），不润色不断句
- 「暴露的处境」写具体处境，不写情绪标签
- 「候选词」= 从这条原话反推出的新长尾词，可空

**⑤ 意图强度与场景类型**
按词库既有取值填：意图强度 `高/中/低`；场景类型 `事件/情境/症状`。判据写一行。

### 5.3 输出

写 `探测原始/probe_<date>_<slug>.result.json`，字段与回填脚本一一对应。**同时在对话里输出人类可读摘要**（做/缓/放弃 + 空缺一句话 + 新词几个）。

### 5.4 明确禁止

- ❌ 不产出「为什么能爆」「hook 类型」「脚本结构」——旧范式产物
- ❌ 不写入 `高热结构库.md`
- ❌ 不联网（联网只在第 1 层）
- ❌ 不推翻脚本算出的 density

## 6. 第 3 层 · 回填脚本 `scripts/xhs-probe/backfill.py`

### 6.1 回填目标与规则

| 目标文件 | 动作 | 幂等键 |
|---|---|---|
| `词库.csv` | 更新 `竞争密度`、`状态` 列 | `关键词` |
| `词库.csv` | 新词（来自 autocomplete / 原话反推）以 `状态=待验证` 追加 | `关键词` 去重 |
| `评论区原话.csv` | 追加 | `来源链接 + 用户原话` 前 20 字 |
| `案例采集卡.md` | 空缺命中自身经历时追加一条待补充线索 | 人工确认，不自动写 |
| `探测日志.csv`（**新建**） | 每轮追加一行 | 独立 schema，10 列 |

> ⚠️ **不写 `运行日志.csv`**（初稿设计有误，已改）。那个文件由采集任务独占，
> `health_check.py` 拿它的**末行日期**与最新 xlsx 日期比对来判断采集是否断流；
> 插进探测行会把末行日期顶新，造成采集断流被掩盖 / 误告警。故另建 `探测日志.csv`：
> `日期,轮次,探测词数,成功数,新增原话数,新增候选词数,小红书状态,密度分布,告警,备注`

### 6.2 硬约束

- **只改指定列**，其余列原样透传（`发布日`、`搜索来源占比`、`关联案例ID` 由别的流程维护，禁止触碰）
- **写前备份**：`词库.csv` → `.bak/词库_<timestamp>.csv`，保留最近 10 份
- **状态机**：`待验证 → 已验证`（探测成功）/ `→ 放弃`（density=高）/ 保持 `待探测`（completeness≠full）。**已使用 / 已验证的行不被降级**
- **写 `运行日志.csv` 必须 10 列**，数值列 2/3/4/5/7 必须是数字，否则 `health_check.py` 09:30 会告警

## 8. 实施顺序与验收标准

### P0 · 提取脚本跑通（先做，其余全部依赖它）
- 交付：`scripts/xhs-probe/probe.py` + `探测原始/` 目录 + `.gitignore` 补充
- 验收：拿词库里 **5 个「待探测」词**跑一轮，产出 5 个 JSON；其中 ≥3 个 `completeness=full`；**全程不触发验证码**
- 若触发验证码 → 先调限速参数，此项不过不进 P1

### P1 · 阈值校准

### 关键问题：基准本身可能不可靠

不建议直接调阈值去迎合人工标注，理由：

1. **存在完全反向的样本**。`绩效面谈被打低分怎么开口` 客观数据是中位数 125.5、低赞占比 40%——
   按任何合理阈值都属于低竞争，人工却标「高」并「放弃」。单纯调阈值无法同时满足它和 `总经理终面`（1069赞/12.5%，人工也标「高」），
   两者客观值差 8.5 倍却是同一标签。
2. **「竞争密度」列可能混入了别的决策维度**。词库里 `跨部门不配合怎么推动` 竞争密度=待探测 但状态=放弃，
   证明「放弃」不必然由密度驱动——可能是赛道不符、案例库无素材等。人工填密度时也可能夹带了这类判断。
3. 两个人工标「低」的词客观值（418/431 赞，15~18% 低赞）明显高于两个脚本标「低」的新词（66/37 赞，70~75% 低赞），
   说明人工的「低」与脚本的「低」不是同一把尺。
