## T1 交互式会话限制上下文窗口（本轮最大收益，~$400/周）
- [x] 配置已改 · 待长会话实测验收
- **根因找到了**：`settings.json` 里的 `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE: 50` **不是有效配置键**，
  所以从来没生效过（这就是上下文能涨到 980k 的原因）。CLI 里的真实键是
  **`autoCompactWindow`**，schema 为 `int().min(1e5).max(1e6)` —— 整数 token 数，100k–1M。
  对应的命令行开关是 `--autocompact <auto|tokens>`。
- **已做**：`~/.claude/settings.json` 加 `"autoCompactWindow": 200000`（备份在
  `settings.json.bak-20260818`）。失效的 `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE` 保留未删 ——
  它无害，但**别再拿它当调节旋钮**。
- **问题**：实测最大的一个会话跑了 927 次请求，上下文一路涨到 **980k** 才 autocompact，
  读缓存累计 **434M = $217**（单会话）。46 个交互式会话 8 天读了 1,670M token，
  占交互式成本的 73%（$835）。
- **改法**：`~/.claude/settings.json` 里设 autocompact 窗口 200k（或每次 `claude --autocompact 200000`）。
  长重构会话主动分段，一段做完 `/clear` 再开下一段。
- **验收**：
  1. 设置后跑一个 ≥200 请求的会话，逐请求 `cache_read_input_tokens` 峰值 ≤ 250k
     （用 `scratchpad/scan.py` 同款统计脚本核）
  2. 该会话 $/请求 比改前同量级会话低 ≥40%
  3. 压缩后任务没断线（能接着干，不用重新交代背景）
- **产出**：`~/.claude/settings.json`
- **依赖**：无

  2. v2「失分最大的维度是不是正文/CTA」→ 14 份仍**全判结构**。因为选题(32)、标题(35)
     满分最高，绝对失分天然最大，正文(10)/CTA(5) 永远赢不了这个比较。
- **边界**：`gap ≤ 0`（分数已过线却仍在返工队列）判结构 —— 那卡的是红线，改正文碰不到。
- **失败可回退**：定向修订后分数没涨 → 立刻切回全量重写，不在这一档耗完剩余轮次。
- **实测体积**：定向修订 prompt 4,841 字 vs 全量重写 54,092 字（**−91%**）
- **产出**：`refine_loop.py`：`classify_rework` / `REWORK_FIX_PROMPT` / `rework_fix_body`
  + `rework_one` 接上分档与回退
- **待验证**：适用面太小，本地凑不出样本。**首次真实触发时看两件事** ——
  ① 复审总分不低于修订前 ② 未被点到的段落逐字未变（diff 校验，别信模型自称）

## T6 标题定向修订（由 T5 的数据牵出来的真正机会）
- [ ] 待办
- **依据**：16 篇未过线稿里，失分最大的维度几乎总是「标题·停不停」（27–30/35）
  或「搜索意图匹配」（26–28/32），而正文维度普遍 8–9/10。
- **为什么值得**：标题只有一行字，prompt 可以只带「标题规则 + 当前标题 + 扣分理由 +
  本篇正文摘要」，估计 <3k 字，比全量重写省 95%。
- ⚠️ **联动风险**：标题改了，首图大字（cards.json 第 1 张）要跟着改，否则首图和标题不一致。
  这是它比正文定向修订复杂的地方，不能只改 md。
- **选题匹配维度改不了**（选题是选定的），那一档只能回到全量重写或直接放弃。
- **问题**：机修档（`MECH_FIX_PROMPT`，621 字 + 正文节，实测 $0.38）已经是定向修订；
  但**分数返工档走 `write_draft()` → `build_prompt()`，50k 字 prompt 全量重建**
  （知识框架、必须命中清单、料包、格式范例一样不少）。
  `refine_loop.py:1041` 的注释自己写着「模型在返工时根本没做定向修改，而是重写」,
  而现有对策全是 prompt 措辞层面的（`:1046` 字数守恒、`:1081`「这是定向返工」）——
  **靠说服模型，而不是靠不给它重写的材料**。
- **改法**：照 `MECH_FIX_PROMPT` 的样子加 `REWORK_FIX_PROMPT`，只喂四样：
  审核报告的扣分点 + 当前正文节全文 + 命中的那几条规则 + 涉及的那几条料。
- **⚠️ 必须分档，不能一刀切**：
  - 局部扣分（引语无出处 / CTA 缺编号选项 / 字数超标 / 数字自相矛盾）→ 定向修订
  - 结构性扣分（开头三句复述同一论点 / 缺整类读者的话术 / 角度与标题不兑现）→ 仍走全量重写
  建议在审核 CSV 里加一个 `修订类型=局部|结构` 字段，由 `rework_one()` 据此选 prompt。
- **验收**：
  1. 局部档 prompt ≤20k 字、单次 ≤$0.50
  2. 定向修订后**复审总分不低于修订前**（返工把分改低过 —— 这正是 `:1041` 那条教训）
  3. 未被点到的段落**逐字未变**（diff 校验，不能靠模型自称）
- **产出**：`scripts/xhs-loop/refine_loop.py`、`scripts/xhs-health/independent_audit.py`
- **依赖**：T2（先把审核链路稳定下来，才能用它衡量返工没退化）

## 明确不做（连同理由，避免下次再想一遍）

- **审核换 Sonnet 5** —— 实测同一篇稿 79 分 vs Opus 86 分，六维普遍低 1–4 分，
  且把「话术模板的场景预演」误判成「编造原话」（正是 T2 台账点名的最大风险）。
  省 $0.44/次，但一次误判返工要赔 $1.80（写稿 $0.98 + 复审 $0.82），
  返工率涨 25% 就倒亏。重新标定 85 分线的成本高于收益。
- **写稿/审核改走 Messages API 直调** —— 理由同第一轮 T4：没有 API key，
  且订阅已覆盖，改造等于把额度消耗变成真实账单。
- **继续压 prompt 字数 / 用检索替代全量塞入** —— 素材侧**已经做完了**：评论区原话
  553→60 条、案例库 200→30 条、词库 1049→1 行、审核侧 T2 反查筛料 148k→24.5k 字。
  剩下的 78.3% 是静态规则区（知识框架 + 必须命中清单 + 红线），它必须每篇全量生效，
  按主题挑三五条会直接漏红线。**同样这批 token，解法是换位置（T2b 缓存），不是砍掉（检索）。**
- **给图库/范例做轻量索引** —— 前提不成立：写稿 prompt 里没有图库（图是写稿产出
  `cards.json` 后另一条链路生成的），历史范例只有 1 篇 1,023 字，占 prompt 2%。
- **抓取/筛选/打标签换便宜模型** —— 已经在做，而且比"便宜模型"更彻底：
  `daily_collect` / `triage_pending` / `auto_analyze` / 写稿首轮全部走 **Gemini Flash 免费层**
  （`XHS_ENGINE` 默认 gemini）。Gemini 免费层 Pro 全系额度为 0，所以返工和审核
  这两个环节接不住，只能留给 Claude —— 这不是没优化，是已经优化到边界了。
