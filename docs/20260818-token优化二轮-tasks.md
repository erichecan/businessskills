## T1 交互式会话限制上下文窗口（本轮最大收益，~$400/周）
- [x] 配置已改 · 待长会话实测验收
- **根因找到了**：`settings.json` 里的 `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE: 50` **不是有效配置键**，
  所以从来没生效过（这就是上下文能涨到 980k 的原因）。CLI 里的真实键是
  **`autoCompactWindow`**，schema 为 `int().min(1e5).max(1e6)` —— 整数 token 数，100k–1M。
  对应的命令行开关是 `--autocompact <auto|tokens>`。
- **已做**：`~/.claude/settings.json` 加 `"autoCompactWindow": 200000`（备份在
  `settings.json.bak-20260818`）。失效的 `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE` 保留未删 ——
  它无害，但**别再拿它当调节旋钮**。
- **问题**：实测最大的一个会话跑了 927 次请求，上下文一路涨到 **980k** 才 autocompact，
  读缓存累计 **434M = $217**（单会话）。46 个交互式会话 8 天读了 1,670M token，
  占交互式成本的 73%（$835）。
- **改法**：`~/.claude/settings.json` 里设 autocompact 窗口 200k（或每次 `claude --autocompact 200000`）。
  长重构会话主动分段，一段做完 `/clear` 再开下一段。
- **验收**：
  1. 设置后跑一个 ≥200 请求的会话，逐请求 `cache_read_input_tokens` 峰值 ≤ 250k
     （用 `scratchpad/scan.py` 同款统计脚本核）
  2. 该会话 $/请求 比改前同量级会话低 ≥40%
  3. 压缩后任务没断线（能接着干，不用重新交代背景）
- **产出**：`~/.claude/settings.json`
- **依赖**：无
- ⚠️ 200k 是估算起点，不是实测最优。压太狠会导致反复重述上下文，反而更贵 ——
  先跑一个会话量一量再定死。

## T2 headless 三链路：+safe-mode +禁 skills +effort medium +静态区搬进 system prompt
- [ ] 待办 · **本轮自动化侧最大收益，周省约 $73**
- **问题**：`claude -p` 每次注入 26.1k 新写 1h 缓存（CLAUDE.md + skills 列表 + 工具定义），
  占写稿单次成本 27%、审核 32%、probe 65%。`headless_cli.py` 注释里「38.7k 是地板价、
  `--bare` 不可用」的结论**已过期** —— `--safe-mode` 保留 auth，实测降到 17.5k，
  再加 `--disable-slash-commands` 降到 14.8k（新写缓存 26.1k → 2.7k）。
- **实测（同一句 5 字 prompt）**：

  | 配置 | 输入合计 | 新写 1h | 读缓存 | 成本 |
  |---|---:|---:|---:|---:|
  | 现状 | 38,811 | 26,106 | 12,703 | $0.268 |
  | +safe-mode | 17,487 | 4,782 | 12,703 | $0.054 |
  | +safe-mode +禁 skills | 14,771 | **2,689** | 12,080 | **$0.033** |
  | +safe-mode +自定义 system prompt | 14,819 | 14,817 | 0 | $0.148 ⛔ |

- **⛔ 不要自定义 `--system-prompt`**：默认 system prompt 那 12k 是跨会话共享的缓存**读**
  （0.1×），换掉就变成每次全新**写**（2×），token 少 5%、成本涨 4.5 倍。

### T2b 静态区搬进 `--append-system-prompt`（8/18 追加，见 `20260818-缓存与prompt结构实测.md`）
- **新发现**：`claude -p` 的**用户 prompt 完全不参与 prompt caching**。实测同一段 prompt
  一字不差重跑三次，写缓存 76.1k 一次不少、读缓存恒定 15.7k；生产数据里批次内连跑 13 篇，
  读缓存同样恒定 15.6k。**8/12 那次「静态在前动态在后」的前缀重排在 CLI 路径下无效**
  （共同前缀从 5.5% 提到 66.7%，但一分钱没省）——`build_prompt` 里那 20 行注释要一起改掉。
- **改法**：prompt 在静态/动态边界切开
  - 写稿：切点在【选题】之前，静态 ~39,200 字（知识框架 14,419 + 必须命中清单 11,045 +
    硬编码红线 ~13,700 + 格式范例 1,023）
  - 审核：切点在 `【词库.csv` 之前，静态 27,340 字
  - 静态段 → `--append-system-prompt`，动态段 → `-p` 的用户 prompt
- **实测收益**（真实审核 prompt，两篇不同成稿）：

  | | 写 1h | 读缓存 | 成本 | 总分 |
  |---|---:|---:|---:|---:|
  | 基线 | 64.1k | 12.7k | $0.879 | 86 |
  | F1 第 1 篇 | 52.8k | 0.0k | $0.666 | 84 |
  | **F2 第 2 篇（换稿）** | **10.1k** | **39.7k** | **$0.285** | 83 |

  13 篇批次均摊 $11.43 → **$4.09（−64%）**；写稿同口径估 −66%。
- **排期约束（重要）**：1h TTL，写稿触发点 11:00 / 15:30 间隔 4.5h → 跨批次必然失效。
  **每批第一篇付全价，第 2 篇起才命中，所以宁可一次多跑几篇，不要把篇数摊到更多触发点上。**
  ⛔ 不要把现在的「2 个触发点 × 各 7–10 篇」改成「4 个触发点 × 各 3–5 篇」。
- **风险**：F1 84 / F2 83，对照基线 86 / E 87，**第一维稳定从 28 掉到 26**，方向一致偏低。
  84 已经贴着 85 发布线。整体波动区间是 83–87（B 在没 append 时也报 84），
  2 个样本分不开「系统性偏严」和「正常波动」。
- **验收**（⛔ 这条是全台账风险最高的一条，验收不能省）：
  1. 取 **8–10 篇已有独立审核分的历史成稿**，用新配置平行复审，
     **总分差中位 ≤2 分、且没有一篇跨过 85 分线**（改档位 = 改发布决策）
  2. 每一篇输出的 CSV 都是 **15 字段**、第 5 字段起是 6 个维度分
     （Sonnet+medium 实测会多插一列且不报错，静默写错台账 —— 必须逐篇校验字段数）
  3. 写稿链路：新配置写 2 篇，独立审核分不低于改前基线
  4. probe 链路：JSON 可解析率 100%
  5. **（T2b 专项）批次内第 2 篇起 `cache_read_input_tokens` ≥ 35k** —— 读不到就说明
     切点选错或静态段里混进了动态内容（日期、关键词、随机排序都会毁掉整个前缀）
  6. **（T2b 专项）静态段必须逐字节稳定**：不含 `date.today()`、不含随机采样、
     不含按 dict 无序遍历生成的内容。改完用同一批输入连生成两次 prompt 做 `diff`，
     静态段必须完全一致
- **产出**：`scripts/headless_cli.py`（改 `HEADLESS_FLAGS`，注释里更新「地板价」的结论）、
  `refine_loop.py::build_prompt`（拆静态/动态 + 删掉失效的前缀重排注释）、
  `independent_audit.py::build_audit_prompt`
- **依赖**：T0（任务得先跑起来才有样本）
- **预期**：单次 $0.879 → 批次均摊 $0.315，三链路合计约 **$73/周**
- **若验收 2 不过**（有稿子跨过 85 线且确认是系统性偏移）：先量幅度是否稳定，
  稳定就把发布线从 85 下调到 83；不稳定就只保留 safe-mode + effort medium，放弃 append 拆分

## T5 分数返工档改成定向修订（周省约 $25）
- [ ] 待办
- **问题**：机修档（`MECH_FIX_PROMPT`，621 字 + 正文节，实测 $0.38）已经是定向修订；
  但**分数返工档走 `write_draft()` → `build_prompt()`，50k 字 prompt 全量重建**
  （知识框架、必须命中清单、料包、格式范例一样不少）。
  `refine_loop.py:1041` 的注释自己写着「模型在返工时根本没做定向修改，而是重写」,
  而现有对策全是 prompt 措辞层面的（`:1046` 字数守恒、`:1081`「这是定向返工」）——
  **靠说服模型，而不是靠不给它重写的材料**。
- **改法**：照 `MECH_FIX_PROMPT` 的样子加 `REWORK_FIX_PROMPT`，只喂四样：
  审核报告的扣分点 + 当前正文节全文 + 命中的那几条规则 + 涉及的那几条料。
- **⚠️ 必须分档，不能一刀切**：
  - 局部扣分（引语无出处 / CTA 缺编号选项 / 字数超标 / 数字自相矛盾）→ 定向修订
  - 结构性扣分（开头三句复述同一论点 / 缺整类读者的话术 / 角度与标题不兑现）→ 仍走全量重写
  建议在审核 CSV 里加一个 `修订类型=局部|结构` 字段，由 `rework_one()` 据此选 prompt。
- **验收**：
  1. 局部档 prompt ≤20k 字、单次 ≤$0.50
  2. 定向修订后**复审总分不低于修订前**（返工把分改低过 —— 这正是 `:1041` 那条教训）
  3. 未被点到的段落**逐字未变**（diff 校验，不能靠模型自称）
- **产出**：`scripts/xhs-loop/refine_loop.py`、`scripts/xhs-health/independent_audit.py`
- **依赖**：T2（先把审核链路稳定下来，才能用它衡量返工没退化）

## 明确不做（连同理由，避免下次再想一遍）

- **审核换 Sonnet 5** —— 实测同一篇稿 79 分 vs Opus 86 分，六维普遍低 1–4 分，
  且把「话术模板的场景预演」误判成「编造原话」（正是 T2 台账点名的最大风险）。
  省 $0.44/次，但一次误判返工要赔 $1.80（写稿 $0.98 + 复审 $0.82），
  返工率涨 25% 就倒亏。重新标定 85 分线的成本高于收益。
- **写稿/审核改走 Messages API 直调** —— 理由同第一轮 T4：没有 API key，
  且订阅已覆盖，改造等于把额度消耗变成真实账单。
- **继续压 prompt 字数 / 用检索替代全量塞入** —— 素材侧**已经做完了**：评论区原话
  553→60 条、案例库 200→30 条、词库 1049→1 行、审核侧 T2 反查筛料 148k→24.5k 字。
  剩下的 78.3% 是静态规则区（知识框架 + 必须命中清单 + 红线），它必须每篇全量生效，
  按主题挑三五条会直接漏红线。**同样这批 token，解法是换位置（T2b 缓存），不是砍掉（检索）。**
- **给图库/范例做轻量索引** —— 前提不成立：写稿 prompt 里没有图库（图是写稿产出
  `cards.json` 后另一条链路生成的），历史范例只有 1 篇 1,023 字，占 prompt 2%。
- **抓取/筛选/打标签换便宜模型** —— 已经在做，而且比"便宜模型"更彻底：
  `daily_collect` / `triage_pending` / `auto_analyze` / 写稿首轮全部走 **Gemini Flash 免费层**
  （`XHS_ENGINE` 默认 gemini）。Gemini 免费层 Pro 全系额度为 0，所以返工和审核
  这两个环节接不住，只能留给 Claude —— 这不是没优化，是已经优化到边界了。
