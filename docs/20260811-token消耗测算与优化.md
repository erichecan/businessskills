## 三、上周优化的实际效果（写稿 prompt 95.6k→33.7k 字）

| 指标 | 优化前(08-06~08, n=86) | 优化后(08-09~11, n=7) | 变化 |
|---|---:|---:|---|
| prompt 字数中位 | 97,802 | 41,370 | **−58%** |
| 单次成本 | $5.57 | $4.58 | **−18%** |
| ├ 写缓存 | $2.84 | $2.10 | −26% |
| ├ 读缓存 | $1.54 | $1.16 | −25% |

**prompt 砍掉 58%，成本只降 18%。** 因为钱不在 prompt 本身 —— 一次写稿会话里有

才是成本主体。压 prompt 的边际收益已经很低了。

> 注：优化后样本只有 7 次真实调用（08-09 的 19 次里 12 次撞额度空转，08-10 全空），

## 五、优化清单（按性价比排序）

### P0 — 审核 prompt 按选题筛料
和写稿同样的改法：不整库塞，按当前选题筛。预计 148k→50k 字，
单次 $3.08→$1.10，日省约 $16，**周省约 $110**。风险：需同步改 prompt 里
「整库喂给你」的措辞（写稿改造时踩过这个坑）。

### P0 — 撞 weekly limit 时立刻停手，不要熬 5 小时
`refine_loop.py:472` 的 `LIMIT_RE` 不区分 session limit 和 weekly limit，
两者都走「等 30 分钟、最多熬 5 小时」。session limit 熬 5 小时是对的，
**weekly limit 要等到周日重置，熬 5 小时纯浪费** —— 08-10 全天 112 次空转就是这个。
改法：匹配到 `weekly limit` 直接 return 并发通知，不进重试循环。
省不了 token（本来就 0），但省掉每天 40+ 次无效唤醒和一整天的假运行。

### P1 — 审核 / probe 改走 Messages API 直调，绕开 CLI
审核 prompt 148k 字（约 100k token），但实测写缓存 311k token —— 多出来的是
Claude Code CLI 注入的 system prompt、工具定义、skills 列表等。这些对单轮
纯文本任务毫无用处。改用 `anthropic` SDK 直调 `messages.create`：
- 去掉 CLI harness 开销（约 −60% 输入 token）
- 缓存 TTL 可控，单轮任务改 5m（1.25×）或干脆不缓存（1.0×），比现在的 2× 省 37–50%

两项叠加，审核成本预计再降一半。probe 同理。

### P1 — 写稿把机械检查移出会话
写稿会话里 14 次 Bash 调用（跑 `draft_check.py` 之类）是成本主体：每次工具
往返都在累积上下文、重写缓存。改成脚本在会话外跑检查，把结果作为下一轮
prompt 的输入。预计请求数 24→5，单次成本 $4.58→$2 上下。

### P2 — 产能仍是消耗的 2.7 倍
`auto_publish.py:74` 的 `DAILY_QUOTA = 3`，而写稿仍是 2 次/天 ×（返工 2 + 新稿 2）
= 8 篇/天。08-08 已从 4 次砍到 2 次，但过剩比仍有 2.7 倍。
砍到 1 次/天（4 篇）仍高于配额，且日省约 $30。

### P2 — 交互式开发会话是最大单项（$895 / 8 天）
08-02 单日 $334，主要是 4.69 亿 token 读缓存。这是开发成本不是生产成本，
但它和自动化流程共用同一个周额度 —— **开发和生产在抢配额**。
建议：重构类长会话尽量安排在自动化任务已完成的时段。
