## 问题 1：Prompt Caching 做到最优了吗？间隔久的定时任务是不是浪费了缓存？

**没有做到最优，而且比"浪费"更严重：用户 prompt 根本没进可复用的缓存池。**

先纠正一个前提：**CLI 用的是 1h TTL，不是 5 分钟**（实测字段是
`ephemeral_1h_input_tokens`，按 2× 计价；5m 那档 CLI 从来没用过）。

### 实验 A：完全相同的 prompt 连跑三次

53k 字符静态文本 + 一句任务，`claude -p` 连续调用，间隔几秒：

| | 写 1h 缓存 | 读缓存 |
|---|---:|---:|
| ① 静态 + 问题A | 75.5k | 15.7k |
| ② 静态 + 问题B | 76.9k | 15.7k |
| ③ **和 ② 完全相同，重跑** | **76.1k** | **15.7k** |

**③ 是决定性的：prompt 一字不差重跑，写缓存一分没少，读缓存纹丝不动。**
那恒定的 15.7k 是 CLI 自己的 system prompt + 工具定义（跨会话共享的那块）。
**用户 prompt 无论内容是什么、重复多少次，都是全新写入、永不读回。**

### 生产数据印证：批次内连跑 13 篇，内容命中率 0%

8/11 06:02 那批（写稿/审核交替，间隔 2.5–5 分钟）：

```
#1  审核  写1h=45.5k  读=15.6k
#2  写稿  写1h=63.3k  读=15.6k
#3  写稿  写1h=60.1k  读=15.6k
…
#13 写稿  写1h=59.6k  读=15.6k
```

**读缓存 13 次全部恒定 15.6k。** 间隔只有 2.5 分钟也没用 —— 不是 TTL 过期，
是那些内容压根没进缓存池。

### 所以：`build_prompt` 里那 20 行「前缀重排」注释是建立在错误假设上的

8/12 那次改动把静态块挪到前面，注释写「实测两篇 prompt 共同前缀只有 2,625 字 = 5.5%，
意味着那 25k 字规则从来没享受过 0.1× 的读缓存」。重排后共同前缀确实从 5.5% 提到
**66.7%**（本次实测），但**一分钱都没省** —— 因为 CLI 的 cache_control 断点打在
system prompt 结束处，用户消息整体不参与前缀匹配。字符串前缀对齐了，缓存边界没对齐。

**直接推论：用户 prompt 每 1k token 的真实单价是 $10/M（2× 写入），不是 $5/M。**
写稿那 40k token 内容 = $0.40，审核 32k = $0.32，全是不可回收的沉没成本。

### 修法：静态区搬到 `--append-system-prompt`

同一段 53k 字符静态内容，换个位置放：

| 配置 | 第 1 次 | 第 2 次起 |
|---|---:|---:|
| 现状（全塞用户 prompt） | $0.798 | **$0.798**（无衰减） |
| `--append-system-prompt` 承载静态 | $0.798 | $0.274（写 23.9k / 读 68.7k） |
| **+ `--safe-mode --disable-slash-commands`** | $0.571 | **$0.046**（写 1.2k / 读 67.4k） |

第二次起降 **94%**。safe-mode 之所以还能再降一截，是因为它去掉了 CLAUDE.md /
skills 那部分每次可能微变的内容 —— 前缀一旦有一个字节不同，后面全部失效，
所以「减少 system prompt 体积」和「稳定 system prompt 内容」在这里是同一件事。

### 回到"间隔久是不是浪费"

改造后这个问题才真正成立，答案是：**跨批次浪费，批次内不浪费。**

- 1h TTL vs 写稿触发点 11:00 / 15:30（间隔 4.5h）→ **跨批次必然失效**，每批第一篇付全价
- 但每批连跑 7–13 篇（8/14、8/16 实测），**第 2 篇起全部命中**
- 13 篇批次的均摊：`(0.571 + 12×0.046) / 13 = $0.086`，相对现状 $0.798 降 **89%**

**所以排期策略要跟着变：宁可一次多跑几篇，不要把篇数摊到更多触发点上。**
现在的 2 个触发点 × 各跑 7–10 篇是对的，不要改成 4 个触发点 × 各 3–5 篇。

⚠️ 待验证的风险：把规则从 user message 挪到 system prompt，模型的遵循方式会变
（system 里的指令通常更"硬"，但对细节清单的逐条落实可能不如 user 消息里的显式列表）。
见下方实测。

## 问题 2：用检索代替全量塞入

**素材侧已经做完了，剩下的大头不是"该检索的素材"，是"该缓存的规则"。**

### 现状盘点：动态素材早就是检索出来的

| 库 | 全库 | 实际进 prompt |
|---|---:|---:|
| 评论区原话 | 553 条 | **60 条**（按关键词 + 场景域筛） |
| 案例库 | 200 条 | **30 条**（强命中全留，弱命中补满预算） |
| 词库 | 1,049 行 | **1 行**（只给本篇关键词那行） |
| probe 探测结果 | 全部 | 2 份（本词相关） |

审核侧在 8/11 的 T2 就做过反查筛料（148k → 24.5k 字，−80%）。写稿侧的
`relevant_quotes()` / `relevant_cases()` 也是同样的做法。**这一步已经到位了。**

### 两个前提要纠正

- **写稿 prompt 里没有图库描述。** 图不在写稿环节 —— 写稿输出 `cards.json`
  卡片文案，配图是后续另一条链路生成的。这块没有可省的 token。
- **历史爆款范例只有 1 篇、1,023 字**（`成稿_2026-08-02_空降前30天.md`），占 prompt 2%。
  不是"整批塞入"，砍掉也省不出什么。

### 真正的大头：静态规则区

写稿 prompt 50,034 字的构成（两个不同选题做 diff）：

| | 字数 | 占比 |
|---|---:|---:|
| 知识框架 | 14,419 | 28.8% |
| 必须命中清单 | 11,045 | 22.1% |
| 硬编码规则（视角红线 / 真实性红线 / 组合边界 / 角度轴…） | ~13,700 | 27.4% |
| 格式范例 | 1,023 | 2.0% |
| **静态小计** | **~39,200** | **78.3%** |
| 动态（关键词 + 料包 + feedback） | ~10,865 | 21.7% |

审核 prompt 同构：74.1% 静态 / 25.9% 动态，共同前缀 27,422 字（67%）。

**这 39k 字不该被检索掉，该被缓存。** 它是红线、骨架、质量标准 —— 每篇都必须
全量生效，按主题挑三五条塞进去会直接掉质量（漏一条红线就是一次返工）。
它每篇一模一样，正是问题 1 里 `--append-system-prompt` 的完美候选。

**结论：检索这条路在本项目已经走到头了；同样这批 token，解法是换位置（缓存），不是砍掉（检索）。**

## 问题 3：模型分级

**分级已经在做，而且比预想的更彻底 —— 便宜的那一档是免费的 Gemini，不是小 Claude。**

| 环节 | 当前 | 评估 |
|---|---|---|
| 抓取 / 关键词筛选（`daily_collect.py`） | **Gemini Flash（免费）** | ✅ 已到位，`XHS_ENGINE` 默认 gemini |
| 待办分诊（`triage_pending.py`） | **Gemini Flash（免费）** | ✅ |
| probe 搜索位分析（`auto_analyze.py`） | **Gemini Flash（免费）**，撞额度回退 Claude | ✅ 8/12 做过三方 A/B，判据一致 |
| 写稿首轮 | **Gemini Flash（免费）** | ✅ |
| 写稿返工 | Opus 5 | 保持 —— 定向理解扣分点，改错地方比不改更糟 |
| 独立审核 | Opus 5 | **保持 Opus，但降 effort**（见下） |

Gemini 免费层的硬边界（8/12 实测）：Flash 全系可用，**Pro 全系额度为 0**
（连一句 hi 都 429）。所以"更便宜的模型"这一档在本项目已经用满了，剩下的
两个环节（返工、审核）恰恰是 Flash 接不住的。

### 审核能不能换更小的 Claude？实测：不能

`docs/20260818-token拆解与模型选择.md` 第五节的 5 组 A/B：Sonnet 5 判 **79 分**，
Opus 判 86 —— 它把「话术模板的场景预演」当成「编造原话」写进红线扣分。
省 $0.44/次，但一次误判返工赔 $1.80，返工率涨 25% 就倒亏。

**能降的是 effort 不是模型**：Opus 5 + `--effort medium` = 87 分、六维分与基线只差 1、
15 字段格式无损，输出 −26%、耗时 −26%。而 Sonnet + medium 虽然也报 86 分，
但 CSV **多插一列且不报错**，会静默把错值写进审核记录。

**你说的选项 E 是对的，再叠加问题 1 的 append-system-prompt。**
"结构化评分标准也能缓存"这句尤其准 —— 审核 prompt 那 27.4k 字静态前缀（skill 正文 +
评分卡 + 红线定义）正是最该搬进 system prompt 的部分。

## 问题 4：返工改成定向修订

**一半已经做了，另一半代码注释里自己承认没做。**

### 已经是定向修订的：机修档

`MECH_FIX_PROMPT` 只有 **621 字** + 当前正文节，明确写着「⛔ 这不是返工，不要重写。
只做修掉这几项所必需的最小改动，其余一个字都别动」。实测单次 **$0.38**，
对比全量写稿 $0.98，**省 61%**。这条路子是对的，已验证。

### 仍在全量重写的：分数返工档

`rework_one()` 走的是 `write_draft()` → `build_prompt()`，**整个 50k 字 prompt 全量重建**
（知识框架、必须命中清单、料包、格式范例一样不少），只是多加一段 feedback。

而 `refine_loop.py:1041` 的注释自己写着：

> 但真正的教训不是阈值调多少 —— 是**模型在返工时根本没做定向修改，而是重写**。

现有对策全是 prompt 措辞层面的（`:1046` 加「字数守恒」、`:1081` 加「这是定向返工：
只改下面点到的问题」）—— **靠说服模型，而不是靠不给它重写的材料**。既然已经知道
模型会重写，就不该继续把整套写作规则和全部料包递到它手上。

### 改法：照机修档的样子做 `REWORK_FIX_PROMPT`

只喂四样：审核报告的扣分点 + 当前正文节全文 + 命中的那几条规则 + 涉及的那几条料。
不喂知识框架、不喂必须命中清单全文、不喂完整料包。

预估：50k 字 → 约 15k 字，写缓存 66.5k → 约 25k，单次 **$0.98 → 约 $0.45**。
按 8/14、8/16 的实际构成（返工约占写稿会话的一半），**周省约 $25**。

⚠️ 需要分档，不能一刀切：
- **局部扣分**（某句引语无出处、CTA 缺编号选项、字数超标、某个数字自相矛盾）→ 定向修订
- **结构性扣分**（开头三句复述同一论点、缺整类读者的话术、角度和标题不兑现）→ 仍需重写

审核报告本来就输出「最高优先级的改一句话」，判档的信息已经有了。
建议：审核输出里加一个 `修订类型=局部|结构` 字段，由 `rework_one()` 据此选 prompt。

## 实测验证：把上面几条合起来，在真实审核 prompt 上跑

不是合成实验 —— 用 `build_audit_prompt()` 的真实输出，在 `【词库.csv` 处切开：
静态 27,340 字 → `--append-system-prompt`，动态 13,576 字 → 用户 prompt。
配置 `--safe-mode --disable-slash-commands --effort medium`，模型 Opus 5。

| | 写 1h | 读缓存 | 输出 | 成本 | 总分 | 六维 | 字段 |
|---|---:|---:|---:|---:|---:|---|---:|
| A 基线（opus/high，全塞用户 prompt） | 64.1k | 12.7k | 9.3k | $0.879 | 86 | 28,30,8,7,8 | 15 ✅ |
| B safe-mode（high，全塞） | 40.7k | 12.1k | 11.3k | $0.696 | 84 | 26,31,8,6,8 | 15 ✅ |
| E safe+medium（全塞） | 52.7k | — | 6.9k | $0.699 | 87 | 28,30,9,7,8 | 15 ✅ |
| **F1 safe+medium+append（第 1 篇）** | 52.8k | 0.0k | 5.6k | $0.666 | 84 | 26,30,8,7,8 | 15 ✅ |
| **F2 同上，换一篇稿（第 2 篇）** | **10.1k** | **39.7k** | 6.6k | **$0.285** | 83 | 26,29,9,6,8 | 15 ✅ |

**F2 是关键：换了一篇完全不同的成稿，静态前缀照样命中 39.7k 读缓存，成本降 57%。**
跨稿件复用成立，不是只有"同一篇重跑"才管用。

13 篇批次的均摊对比：

| | 13 篇合计 | 相对基线 |
|---|---:|---:|
| A 现状 | $11.43 | — |
| E safe+medium | $9.09 | −20% |
| **F safe+medium+append** | **$4.09** | **−64%** |

按写稿链路同口径估算（静态 39.2k 字 ≈ 31k token、动态 10.9k 字 ≈ 9k token）：
单篇 $0.98 → 均摊约 $0.335，**−66%**。

**合起来：定时任务 $17.3/天 → 约 $7/天，周省约 $73。** 这比只上 safe-mode（周省 $35）翻了一倍。

### ⚠️ 但分数偏低 2–3 分，这是唯一的拦路问题

F1 = 84、F2 = 83，对照基线 A = 86、E = 87。第一维（竞争密度/意图强度）稳定
从 28 掉到 26，两篇都是。

观测到的整体波动是 83–87（A 86 / B 84 / E 87 / F1 84 / F2 83），F 落在区间内，
**但方向一致偏低，且 84 已经贴着 85 分线** —— 86 绿档变 84 黄档就是发布决策变了。

两种可能，现在的样本量分不开：
1. 规则搬进 system prompt 后，模型对评分卡的执行确实略严（system 指令更"硬"）
2. 只是正常波动（B 在没有 append 的情况下也报了 84）

⛔ **不能凭这 2 个样本上生产。** 验收方案见台账 T2：取 8–10 篇已有独立审核分的
历史成稿平行复审，看总分差的**中位数**和**有没有稿子跨过 85 线**。
如果确认是系统性偏移且幅度稳定，最省事的解法是**把发布线从 85 下调到 83**，
而不是放弃这套改造 —— 但那需要先证明它是稳定偏移，不是随机变差。
