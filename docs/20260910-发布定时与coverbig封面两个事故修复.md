# 发布定时失败 + coverbig 封面没生效：两个事故的根因与修复

2026-09-10 晚。今天 22:00 全自动发布两篇都卡在「⛔ 没找到小红书发布页 tab」，
且已过审的两篇成品图仍是旧版纯文字封面，不是当天下午刚接入的 coverbig。
两个问题分开查，根因都不在 `refine_loop.py` 那次改动本身。

## 事故一：发布定时找不到 tab

**根因**：`~/.claude/skills/web-access` 的共享 `cdp-proxy.mjs` 在端口 3456 上
出现了一个**脱离 launchd 管理的孤儿进程**（PID 40609，21:21:44 启动，无从查证
是谁起的，大概率是另一个会话手动跑了 web-access 且没设 `CHROME_DEBUG_PORT`）。
它先一步抢占了 3456 端口，且没有 `CHROME_DEBUG_PORT=9333`，于是回退自动发现，
连到了日常 Chrome（端口 9222）。与此同时 `com.eric.cdpproxy.plist`（配置正确、
KeepAlive）反复被这个孤儿挡在外面，`/tmp/cdpproxy.log` 里全是
「已有实例运行在端口 3456，退出」。

`prefill_xhs` / `open_sched_switch` 走的是 3456 这层代理（连着错的 Chrome），
成功把稿子填进了日常 Chrome 里的发布页；而 `set_schedule.mjs` 是**直连 9333**
（对的 Chrome）去找 `creator.xiaohongshu.com/publish` 的 tab —— 那个 tab 根本
不在这个浏览器进程里，自然报「没找到小红书发布页 tab」。日志显示"预填成功
""定时开关已打开"正是因为前两步走的是另一个浏览器，只有最后这一步的连接方式
不一样，才在这里露馅。

**修复**：
1. 当场杀掉孤儿进程，`launchctl kickstart -k` 把 launchd 里配置正确的那份
   拉起来，`/health` 确认 `chromePort:9333`。
2. `scripts/xhs-publish/auto_publish.py` 新增 `ensure_cdp_proxy_healthy()`，
   在真正碰浏览器之前自检一次：不是 9333 就杀掉占端口的进程、kickstart
   正确的 launchd job，重试 3 次仍不行才报错退出。判断权放代码里，不再靠
   人事后翻日志才发现。

## 事故二：封面没用上 coverbig（连带发现的第二个 bug）

`refine_loop.py` 那次改动（`d919f12`）本身没问题——但**今天两篇成品的写稿
时间是 11:37/16:07，改动落地是 20:24**，写在前、改在后，新 prompt 根本没机会
生效。这两篇的 `cards.json` 第一张卡仍是 `"type":"cover"`。

**处理**：没有重新花真实 API 额度整篇重写（正文已过审，85 分/84 分），改成
直接把这两篇的封面卡按新规格手工改：`type` 改 `coverbig`、挑 3-5 字判断词包
`<span class="hl">`、按内容选一个没在本篇其余 6 张卡里出现过的 pose，再用
`make_cards.py` 重新渲染这一张图。

**渲染时又炸出第三个 bug**：`scripts/case-entry/case_entry.py` 的
`ensure_cover()` 只认死文件名 `01_cover.png` 来判断"封面是否已渲染"。
coverbig 改版后真封面文件名变成了 `01_coverbig.png`，这个判断永远读不到
"已有封面"，于是每次 `prefill_xhs` 都会用旧版纯文字模板现渲一张
`01_cover.png` 塞进同一个目录——而 `prefill_xhs` 按文件名字典序上传全部图片，
`01_cover.png` 排在 `01_coverbig.png` 前面。

**后果比预想的更糟**：「试用期过了没谈转正」那篇已经在这个 bug 生效期间跑完
了一次全自动发布并成功定时——**发出去的 8 张图里，第一张是旧版占位封面，
真正的 coverbig 封面被挤到第二张**。发现后没有选择"删了重来"（发布页日历
那步本来就脆，重排一次时段就变了），而是：

1. 打开这篇已定时笔记的编辑页（`creator.xiaohongshu.com/publish/update?id=...`），
   先读一遍 `.post-time-wrapper` 确认定时开关和时间没被状态污染。
2. 用真实坐标的 `mousedown/mouseup/click` 三连事件点掉第一张图（`img-idx=1`）
   的 `close-btn`，图片数从 8 降回 7，核对剩下 7 张确实是 coverbig 打头。
3. 再读一遍定时状态确认没变（`2026-09-11 22:00`、开关仍是 on），才对
   `<xhs-publish-btn>` 派发 `publish` 自定义事件保存——这条"改完直接派发
   publish 事件，定时排期不变"的路径是抄 `fix_topics.py` 里已经验证过的做法，
   没有另起一套没试过的点击流程。
4. `fix_topics.scheduled_notes()` 回读笔记管理，确认两篇都还在定时队列里，
   时间没变。

`ensure_cover()` 已改成用 `01_cover*.png` 通配匹配，不再猜死后缀。
